- **In one paragraph:** Arran Cudbard-Bell (FreeRADIUS) fixed the calendar tool in one afternoon,
  in three steps. First he repaired the AppleScript: locale-proof dates, a calendar lookup that
  really searches, full escaping, and real list and search in place of upstream's stubs. Next he
  swapped the slow `whose` filter for a date-range form. Finally he threw the AppleScript out and
  moved list, search, create, update and delete onto `utils/calendar-query`, a small EventKit
  command-line tool. Its **Swift source is committed** (`utils/calendar-query.swift`, 184 lines),
  and so is **a prebuilt universal binary** (366 KB, x86_64 + arm64, ad-hoc linker signature, no
  embedded Info.plist, no build script). Nothing links the two reproducibly. The tool is the
  closest thing among the forks to plan.md's Swift helper, and it confirms EventKit is the
  right mechanism. Values travel as argv and JSON, never as script text, so there is no
  injection. As a design it falls short:
  - One process per call, blocking Node for up to 10 s.
  - No protocol version and free-text errors.
  - Unparseable dates silently replaced or ignored.
  - A denied permission shows up as "no events".
  - **Recurring events handled wrongly**: every occurrence shares one id, and update or delete
    hits the earliest occurrence in a four-year window, not the one the agent meant.

## How it reaches each app

| Context | Mechanism | Notes |
|---|---|---|
| Calendar (list, search, create, update, delete) | `execFileSync(utils/calendar-query, [verb, …args])`, 10 s timeout, one process per call; the binary uses `EKEventStore` | No shell, no script. The binary is committed prebuilt next to its source. |
| Calendar (open, access check) | AppleScript via `run-applescript` (unchanged) | `getEvents`/`searchEvents` still gate on `tell application "Calendar" to return name` before running the binary. |

**The binary's protocol (as committed):**

| Verb | Arguments | Success output (stdout) |
|---|---|---|
| `list` | `<from> <to> [limit=20]` | JSON array of `{id, title, startDate, endDate, calendarName, isAllDay, location?, notes?}` |
| `search` | `<text> <from> <to> [limit=20]` | Same array; lower-cased substring match on **title only** |
| `create` | `<calendar_name> <json: {title, startDate, endDate, isAllDay?, location?, notes?}>` | the new event's `eventIdentifier` |
| `update` | `<event_id> <json: {title?, startDate?, endDate?, location?, notes?}>` | the `eventIdentifier` |
| `delete` | `<event_id>` | `deleted` |

- **Ids:** `EKEvent.eventIdentifier`.
- **Dates out:** ISO 8601 in UTC with fractional seconds.
- **Dates in:** `ISO8601DateFormatter` with `.withFractionalSeconds` (so `2026-05-04T10:00:00Z`
  **fails**), or else `yyyy-MM-dd` at local midnight.
- **Errors:** one line of free text on stderr and exit code 1: `calendar access denied`,
  `event not found`, `create: invalid dates`, `create failed: <NSError>`. The TS side matches
  the substring `"event not found"`.
- **Missing pieces:** no protocol version, no request id, no structured error codes.

## Changes

### C1 Listing and searching events returns the user's real events

- **Kind:** fix
- **Context:** calendar
- **Symptom:** Listing events returned one fake event titled "No events available - Calendar
  operations too slow". Search always returned nothing.
- **Root cause:** Upstream gave up. `getEvents` builds a hard-coded dummy event
  (`utils/calendar.ts:96-117`) and `searchEvents` returns an empty list without searching
  (`utils/calendar.ts:170-178`). Even a real result would have been dropped, because the
  string result goes through `Array.isArray` (`utils/calendar.ts:120-123`).
- **Technique:**
  - `3a26c9a`: an AppleScript loop over calendars with
    `events of c whose start date ≥ … and start date ≤ …`, dates built component by component.
  - `1027ad1`: `events of c from startDate to endDate`. The commit says the `whose` form "triggers
    remote calendar syncs" and is "unusably slow on Google-synced calendars".
  - `9097294` replaces both with EventKit:
    `predicateForEvents(withStart:end:calendars:nil)`, then `events(matching:)`, then
    `prefix(limit)` and JSON.
- **Evidence:** `3a26c9a`, `1027ad1`, `9097294`. Upstream #74 (no entries found), #25 (missing
  events), #70, #6.
- **Quality of the fix:** partial.
  (a) The list is truncated with `prefix(limit)` and never sorted by start date. EventKit
  doesn't document an order, so the first N events can be arbitrary.
  (b) A date-only `to` means midnight at the *start* of that day, so the last requested day is
  left out. `3a26c9a` had used 23:59:59.
  (c) The tool schema invites "ISO format", but an ISO date-time without fractional seconds
  doesn't parse. The binary then silently substitutes now … +7 days (list) or −1 y … +3 y
  (search) and still reports success.
  (d) The TS default range uses `toISOString().split('T')[0]`, a UTC date, so near midnight
  "today" is the wrong day.
  (e) Search matches titles only, though the tool description promises "titles, locations, and
  notes".
  (f) Any failure is caught and returned as `[]`.
  (g) Recurring events come back as several entries with the same `id` and nothing else to tell
  them apart (see C3).
- **Verdict:** adopt the idea (EventKit range query, as plan.md already chooses). The AppleScript
  `from … to …` claim is superseded, so it needs no verification.
- **Scenarios:**
  - [acceptance] `listing events` — `given events across several calendars this week, reports them in start order with their calendar named`
  - [domain] `a date range` — `given an end day, includes every event starting on that day`
  - [domain] `a date range` — `given a date that cannot be read, refuses it rather than choosing another range`
  - [acceptance] `listing events` — `given more events than the limit, reports the earliest ones and says more exist`
  - [acceptance] `searching events` — `given the text appears only in an event's location or notes, finds the event`

### C2 A new event lands on the requested calendar at the requested time in any locale

- **Kind:** fix, hardening
- **Context:** calendar
- **Symptom:** Creating an event failed silently, landed at the wrong time on non-US locales or
  across DST, or landed on some other calendar.
- **Root cause:**
  - Upstream coerces `date "${start.toLocaleString()}"` (`utils/calendar.ts:270-271`), and
    AppleScript's date parsing depends on the system locale.
  - It looks up `calendar "${targetCalendar}"` without escaping and falls back to
    `first calendar` (`:276-280`).
  - It escapes only `"` in the title (`:284`), and splices location and notes in unescaped
    (`:286`, `:290`).
  - It returns Calendar.app's `uid`, which the commit says doesn't match EventKit's
    `eventIdentifier`.
- **Technique:**
  - `3a26c9a`: `set year/month/day/hours/minutes of d`, a `repeat` loop matching
    `name of c is "<escaped>"` with `missing value` as the fallback, and `\` then `"` escaping on
    every value.
  - `9097294` replaces this with an EventKit `create` given ISO instants from
    `Date#toISOString()` as JSON argv.
  - The calendar is `calendars(for: .event).first { $0.title == name }`, falling back to
    `defaultCalendarForNewEvents`.
  - `save(event, span: .thisEvent, commit: true)`, and the result is the `eventIdentifier`.
- **Evidence:** `3a26c9a`, `9097294`. Upstream #34 (wrong time parsing), #74.
- **Quality of the fix:** partial.
  (a) An unknown calendar name, or none (TS defaults to the literal `"Calendar"`), silently
  goes to the default calendar, and the result doesn't say which calendar was used.
  (b) Calendar titles aren't unique across accounts, and the first match wins.
  (c) For `isAllDay`, UTC instants are stored as they are, so the all-day date can shift by a day
  (verify).
  (d) The success depends on `save` not throwing, a real store signal, but nothing is read back.
  (e) Writing is always enabled.
- **Verdict:** adopt the idea (typed instants through EventKit, calendar chosen explicitly). Verify:
  *an all-day event created from `2026-05-04T00:00:00.000Z` in a UTC−5 zone appears on 3 May.*
- **Scenarios:**
  - [acceptance] `creating an event` — `given a calendar name that does not exist, refuses and names the calendars that do`
  - [acceptance] `creating an event` — `reports the calendar and times the store actually saved`
  - [contract] `an event store` — `given a system locale that writes dates day-first, saves the event at the instant given`
  - [domain] `an all-day event` — `given a day, occupies that day in the user's time zone`
  - [acceptance] `creating an event` — `given calendar writing is not enabled, refuses: writes are off by default`

### C3 Updating and deleting an event by its id

- **Kind:** feature
- **Context:** calendar
- **Symptom:** Upstream couldn't change or remove an event. Its create returned an id nothing
  else could use.
- **Root cause:** Upstream's calendar tool offers only search, open, list and create
  (`tools.ts` `CALENDAR_TOOL`). `openEvent` just activates Calendar
  (`utils/calendar.ts:317-355`).
- **Technique:** `update <id> <json>` and `delete <id>`. `findEvent` loads every event from now −2 y
  to now +2 y and takes the **first** with a matching `eventIdentifier`. Then
  `save`/`remove(span: .thisEvent, commit: true)`. Only title, start, end, location and notes can
  change.
- **Evidence:** `9097294`.
- **Quality of the fix:** wrong for recurring events, partial otherwise.
  (a) **Recurring events:** EventKit expands a series into occurrences that all share one
  `eventIdentifier`. `findEvent` returns the earliest occurrence in the window (up to two years
  ago), and `.thisEvent` changes or deletes that one, not the occurrence the agent listed. There's
  no way to address a specific occurrence or the whole series (`.futureEvents`). `list` doesn't
  expose recurrence either.
  (b) Events more than 2 years away can't be found, although EventKit offers a direct id lookup
  (`event(withIdentifier:)`).
  (c) An update date that fails to parse is **silently skipped**, and the tool still says "Event
  updated."
  (d) No check that start is before end on update. The calendar and all-day flag can't be
  changed.
  (e) Delete runs straight away, with no opt-in or confirmation. The tool schema still describes
  `eventId` as for "open and delete" and says nothing about the update fields.
- **Verdict:** adopt the idea (id-addressed update and delete through EventKit). Reject the
  technique. An occurrence must be addressed as series id plus occurrence start, and the scope
  (this occurrence, this and future) must be explicit.
- **Scenarios:**
  - [domain] `an occurrence` — `is identified by its series and its original start, since every occurrence of a series shares one event id`
  - [acceptance] `rescheduling an event` — `given a weekly series, moves only the occurrence asked for`
  - [acceptance] `deleting an event` — `given a recurring event and no scope, refuses: it cannot tell one occurrence from the whole series`
  - [acceptance] `rescheduling an event` — `given a new start that cannot be read, refuses and changes nothing`
  - [acceptance] `rescheduling an event` — `given an event years away, still finds it by its id`

### C4 Calendar goes through a bundled EventKit command-line tool

- **Kind:** infra
- **Context:** calendar
- **Symptom:** AppleScript calendar queries were slow, locked Calendar.app and blocked on remote
  sync (per the commit).
- **Root cause:** Scripting Calendar.app goes through Apple Events and the app's own sync, one
  property fetch at a time (upstream `utils/calendar.ts`, whole file).
- **Technique:** `utils/calendar-query.swift` compiled to a universal binary and committed, called
  once per operation with argv (protocol table above). JS finds it at
  `dirname(import.meta.url)/../utils/calendar-query`.
- **Evidence:** `9097294`.
- **Quality of the fix:** partial.
  (a) The committed binary can't be reproduced: there's no Package.swift or build script. Its
  strings match the source (`usage: calendar-query …`, `calendar access denied`,
  `main/calendar-query.swift`), but identity is unproven. It is signed ad hoc and has no
  Info.plist, so it carries no usage description.
  (b) A fresh process per call pays EventKit setup and the permission request every time, and
  `execFileSync` freezes the server while it runs.
  (c) No protocol version, and errors are free text matched by substring.
  (d) `try!` on JSON encoding crashes the process instead of reporting an error.
- **Verdict:** adopt the idea (EventKit behind a Swift helper, values as argv/JSON, with the
  source in the repo). Reject: a prebuilt binary committed without a build, one process per call,
  and an unversioned free-text protocol. plan.md's long-lived, versioned JSON-lines helper
  replaces all three.
- **Scenarios:**
  - [contract] `the native helper` — `given a request for a protocol version it does not speak, refuses with a version mismatch`
  - [contract] `the native helper` — `given the store fails, answers with a named failure rather than free text`
  - [contract] `the native helper` — `keeps serving other requests while one calendar query runs`

### C5 Calendar permission is requested through EventKit, but a denial reads as "no events"

- **Kind:** hardening
- **Context:** calendar
- **Symptom:** Upstream never really asked for Calendar access (#65 for contacts is the same
  pattern). Its instructions point at Automation settings.
- **Root cause:** Upstream tests access with `tell application "Calendar" to return name`, which
  is the Automation permission, not the Calendars one (`utils/calendar.ts:27-67`).
- **Technique:** The binary calls `requestFullAccessToEvents` on macOS 14+ and
  `requestAccess(to: .event)` before that. If access isn't granted it writes
  `calendar access denied` to stderr and exits 1. On the TS side:
  - `getEvents`/`searchEvents` still run the AppleScript Automation check first, which launches
    Calendar.app and needs a *different* permission.
  - They then catch the binary's failure and return `[]`.
  - `createEvent` dropped the Automation check and surfaces the raw
    `Command failed: … calendar access denied`.
- **Evidence:** `9097294`. Upstream #65 (pattern), #71 (permission manifest).
- **Quality of the fix:** partial. The right EventKit call is used. But a denial on list or search
  is indistinguishable from an empty calendar. Two permissions are needed where one would do. And
  no failure says which setting to change.
- **Verdict:** adopt the idea (request full calendar access through EventKit on macOS 14+). Verify:
  *when a helper binary with no Info.plist calls `requestFullAccessToEvents` from a process
  started by Claude Desktop or a terminal, macOS shows the prompt and attributes the grant to
  the responsible app rather than denying silently.*
- **Scenarios:**
  - [acceptance] `listing events` — `given calendar access is denied, reports a permission failure naming Privacy & Security › Calendars`
  - [contract] `an event store` — `given access has never been asked for, asks for full access once`
  - [acceptance] `listing events` — `needs calendar access only, never permission to control the Calendar app`

## Glossary candidates

- **event:** an `EKEvent`, identified by `eventIdentifier`. The fork's API uses that id for
  create, update and delete.
- **occurrence:** one instance of a recurring event in a date range. In EventKit it shares the
  series' `eventIdentifier`, so the id alone does not identify it.
- **span:** how far a change to an occurrence reaches: `thisEvent` or `futureEvents`.
- **uid (Calendar.app):** the AppleScript `uid` property. The commit says it is not the EventKit
  `eventIdentifier`.
- **calendar:** an `EKCalendar`, looked up by `title`, which is not unique across accounts.
- **default calendar for new events:** the store's `defaultCalendarForNewEvents`, used as the
  silent fallback.
- **full access / write-only access:** EventKit's two access levels on macOS 14+. The fork asks
  for full access.
